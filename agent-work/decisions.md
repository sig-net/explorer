# Decisions

Append only. An agent that disagrees with an entry reports it and never acts against it.

`Decided by` is `user`, `planner` for how the thing is built, `planner (unconfirmed)` for what changes what the user gets until they have confirmed it, then `planner (confirmed)`, or `orchestrator` during execution.

| No. | Decision | Why | Decided by |
| --- | --- | --- | --- |
| D01 | The explorer gets a long running Node backend and a SQL database. The UI reads Midnight data from the backend alone. | Since the ledger 9 upgrade no public Midnight node or indexer serves a browser, and the tool must stay available to clients of the sig integration. | user |
| D02 | The earlier attempt's `agent-work/` is removed unread, and the design starts again from the code and the conversation. | The user's instruction. | user |
| D03 | The database is PostgreSQL. | A long running server with one writer per network and concurrent readers, trigram search and JSON aggregation, all measured in A5. | planner (confirmed) |
| D04 | Networks are separated by one PostgreSQL schema per network, with identical tables. | A wipe is one `DROP SCHEMA`, no query can forget a network filter, and one set of migrations serves every network. Named tables per network would need the same statements generated per name. | planner (confirmed) |
| D05 | The request list is served from a `requests` table the ingest transaction maintains, one row per request id, and the `lifecycle` view joins each row to its events. The table is written by the backend's code inside the ingest transaction, with no database trigger. | A5: a plain view took 1.4 to 3.1 s at 1.5 million requests, the table under 4 ms. Application code keeps the aggregation in one tested place and the table can be rebuilt from `events`. | planner (confirmed) |
| D06 | The cursor of a network moves in the same SQL transaction that stores everything read up to it, and only when it still holds the value the read started from. | A crash or a failed read then leaves the cursor before the missing data, and two backends cannot both advance it. | planner (confirmed) |
| D07 | The backend inspects each request's transaction when it ingests it and stores the request record. The browser stops loading the ledger WebAssembly. | The raw transaction came from the indexer, which the browser can no longer reach, and the inspection of a finalised transaction never changes. | planner (confirmed) |
| D08 | The production backend reads Midnight from Blockfrost's indexer, with the project token held on the server. The indexer adaptor is the one built. | The user's answer to Q1. The SDK's indexer source already yields decoded events for a block range. | user |
| D09 | The backend and PostgreSQL run in Kubernetes on Google Cloud. The task delivers a Docker image for the backend and no GitHub Actions workflow. The UI stays on GitHub Pages and calls the backend across origins, so the backend answers CORS. | The user's answer to Q2. | user |
| D10 | EVM transaction status, EVM tracing and the MPC output cache stay in the browser. | The user's answer to Q3. They need no Midnight node or indexer. | user |
| D11 | Contract addresses, the source URL and the starting block are server configuration. The UI still shows them, read only, for information. A developer on a local `undeployed` stack runs the backend locally. | The user's answer to Q4. | user |
| D12 | When a network's genesis hash or contract addresses differ from what its schema was indexed for, the backend stops that network, reports it unhealthy and waits for an operator's wipe command. | The user's answer to Q5. A misconfigured variable then cannot erase a network's history. | user |
| D13 | The API returns the source URL without its query string, so the Blockfrost token never reaches a browser. | D11 shows the source URL in the UI, and the token is a server secret (D08). | planner |
| D14 | The image covers the backend alone: no Kubernetes manifests and no workflow. The backend runs its migrations at start, takes its configuration from the environment, serves a liveness and a readiness endpoint, and stops cleanly on SIGTERM. The allowed CORS origins are a configuration value. | What a Kubernetes deployment needs from an image (D09), and the manifests belong to whoever owns the cluster. | planner |
| D15 | The row of the request list is assembled when read: the `lifecycle` view joins the maintained `requests` row to its rows in `events` and `transactions`. No copy of the events is stored in `requests`. | The user's answer to Q6. Each event is stored once, and A5 measured the join at 0.8 ms for 50 rows. | user |
| D16 | The four packages are private workspaces named `@sig-net/explorer-ui`, `@sig-net/explorer-lib`, `@sig-net/explorer-api` and `@sig-net/explorer-backend`, under `packages/`. | The user's layout (O7), named after the repository. | planner |
| D17 | The backend is built on Hono (HTTP), Kysely with `pg` (typed SQL), zod (validation) and plain SQL migration files. Node runs its TypeScript sources directly, in tests and in the image, with no build step. | Each is small and typed, which the repository's type rules need. Node 24 and 26 run the sources and resolve the workspaces, probed in the core pack. | planner |
| D18 | A network's schema is named `midnight_<network id>`. | The network ids are Midnight's, and a second chain would bring ids of its own. | planner |
| D19 | The indexer's event id is the primary key of `events` and the order of everything. | It is unique across contracts and ascended over the whole preprod history (A4). The indexer is the one source (D08). | planner |
| D20 | The API is read only under `/v1`: the networks with their configuration and sync state, a page of lifecycles, one lifecycle by request id, the callers of a network. An event crosses the wire as its raw payload and the browser decodes it with the SDK. | One decoder for both sides cannot drift, and the browser's checks then rest on the bytes the contract emitted. | planner |
| D21 | The backend polls each network every 30 seconds by default, reads at most 2,000 blocks a cycle, and each is a configuration value. Stage 1's gates may lengthen the default. | 30 seconds is about 8,640 polls a day per network, and the quota of the Blockfrost plan is not known (A10). | planner |
| D22 | The request list loads 50 lifecycles and a "Load more" button loads the next 50. Search and caller exclusion are answered by the backend. Refresh re-reads the first page. A linked request is read by its id. | The browser no longer holds the whole history, which is about 500,000 requests a year (A3). | planner |
| D23 | A transaction whose inspection throws is stored as a failed inspection with the reason, and the ingest goes on. A raw transaction that cannot be fetched fails the cycle, which is retried. | A transaction our decoder cannot read must not stop the network for ever, while a failed fetch is a gap if it is skipped. | planner |
| D24 | Tests that touch the database run against a real PostgreSQL named by `EXPLORER_TEST_DATABASE_URL`, and fail when it is unset. | The view, the trigram search and the transactions are PostgreSQL's own behaviour. A skipped test would pass with nothing tested. | planner |
| D25 | There are two Dockerfiles, `packages/ui/Dockerfile` and `packages/backend/Dockerfile`, both built from the repository root. The workflows that name the old root `Dockerfile` and `dist` are left for the user, with the exact change each needs in the closing report. | A second image makes a bare `Dockerfile` ambiguous, and this machine cannot push a workflow change. | planner |
| D26 | The raw bytes of each request's transaction are kept in the database beside the inspection result. | They allow every stored transaction to be inspected again after a fix to the decoder, without the indexer. The cost is about 12.6 KB a request (one sample), about 6 GB a year per network at preprod's rate. | planner (confirmed) |
| D27 | Outcome of gate A7: the ingest needs no tip margin for late events. | The 30 minute soak of preprod (blocks 3442003 to 3442279, 91 events read twice) found `lateEvents` 0 and `vanishedEvents` 0. | orchestrator |
| D28 | Outcome of gate A8: `tipMargin` defaults to 6 blocks. | The soak found the indexer's tip ahead of finality by at most 1 block (4 polls of 361) with `tipHashMismatches` 0, and the gate sets the margin to at least n + 5. | orchestrator |
| D29 | Outcome of gate A10: the default poll interval of 30 seconds stands (D21). | All 1,911 calls of the soak answered 200, at about seven times the ingest's planned rate. The daily quota of the plan is still for the user to confirm. | orchestrator |
| D30 | The repository root has no `tsconfig.json`. Each workspace typechecks itself with its own. | Measured in a scratch copy of the workspace layout at 2adc538: type-aware oxlint run from the root reports the same finding with and without a root file, and no script reads one. | orchestrator |
| D31 | A developer's `.env.local` for the UI lives in `packages/ui/`, where Vite reads it. `vite.config.ts` sets no `envDir`. | The file configures the UI alone, and the backend takes its configuration from its own environment (D14). | orchestrator |
| D32 | `@sig-net/explorer-lib` has a second entry, `@sig-net/explorer-lib/testing`, which holds the lifecycle fixture alone. The two event fixtures stay in the UI, and lib does not depend on `luxon`: what moves builds its dates with `Date`. | The lifecycle fixture is used by tests of lib and of the UI, the event fixtures by UI tests alone (grep at 2adc538), and a new dependency of lib would change `yarn.lock` outside step 02.3's scope. | orchestrator |
| D33 | Outcome of the gate of stage 3: the request record crosses the wire as the cell the transcript wrote (each atom as hex, the alignment as the ledger's JSON), and the browser decodes it with the SDK's `decodeEvmType2SignBidirectionalEvent`. No field by field codec is written. | `probes/request-cell-wire.mjs` at c09a270 took the cell of the preprod fixture transaction through JSON and back: the decoded records are equal and the record still hashes to its request id (`probes/request-cell-wire.out`). One decoder for both sides, as D20 wants for events. | orchestrator |
| D34 | A transaction's stored inspection is `{ callChains, requestCells }`, with one cell (or null) per sign bidirectional event of the transaction under that event's id, or `{ failed: reason }`. On the wire each sign bidirectional event carries `{ callChains, requestCell }` for itself, or `{ failed }`. | The inspection reads the record of one notification (`inspectSignBidirectionalTransaction(raw, requestId, notification)`), a transaction may notify several requests, and the store keeps one inspection per transaction. The UI of today keeps one result per transaction and request. | orchestrator |
| D35 | The api package's domain inspection of a sign bidirectional event is `{ callChains, request, requestCell }` or `{ failed }`: the wire cell is kept beside the record decoded from it. | `lifecycleToWire` must emit the cell and D33 forbids an encoder, so a service that holds domain lifecycles has to carry the cell (report of 03.1). | orchestrator |
| D36 | The store keeps every caller of a request in a table `request_callers (request_id, caller)` with a trigram index, and `requests` has no `caller` column. | Review 03.3, blocking: the API, the in-memory service and the UI search, exclude and list every caller of a request, and the UI gives each one a hide button. Narrowing them to the first caller would take from what the user has today. | orchestrator |
| D37 | A page of lifecycles carries `matchingEvents`, the events of the requests that match the search and the exclusion. | Review 03.3, blocking: the UI's status line shows matching events over all events, and the page had no field for it. The store gives it as a sum of the count columns of `requests`. | orchestrator |
| D38 | Replaces the stored half of D34: a transaction's stored inspection is `{ callChains, requests: { "<event id>": { cell: cell or null } or { failed: reason } } }`, or `{ failed: reason }` for the whole transaction. The wire half of D34 stands. | Review 03.3: the inspection runs per notification and may fail for one of them (D23), which a single result per transaction could not store beside a read one, while the in-memory service holds one result per event. | orchestrator |
| D39 | The source URL crosses the wire without its user and password as well as without its query string. Extends D13. | Review 03.3: the cut kept `user:password@`. | orchestrator |
| D40 | Outcome of the gate of stage 3: the two blocking findings of review 03.3 are closed by D36 and D37 (step 03.4), and the review of that fix (03.6) found nothing blocking. The advisory findings of both reviews that concern the service and the ingest are requirements of stage 4. | The stage's gate allows two reviews, and both are spent. | orchestrator |
| D41 | A search fragment of fewer than 3 characters is no search: it matches every lifecycle. The rule lives in `resolveLifecyclesQuery` of the api package behind the constant `LIFECYCLES_MIN_SEARCH_LENGTH`, so every service follows it, and the UI says so under the search box. | Review 03.6: a fragment of 1 or 2 characters has no trigram, and its counts took up to 1006 ms at 200,000 requests. An `invalid_request` would turn the first two keystrokes into an error. | orchestrator |
| D42 | The served search is always the UNION form: `request_id IN (SELECT request_id FROM requests WHERE request_id LIKE x UNION SELECT request_id FROM request_callers WHERE caller LIKE x)`, with backslash, percent and underscore escaped in `x`. A fragment that matches a large share of the requests is accepted as slower. | Review 03.6 at 200,000 requests: pages 1.4 to 7.3 ms and counts under 3 ms against 55 to 103 ms for the OR form. The UNION form loses only on a fragment matching 80,000 requests (129 ms), and one form is one thing to test. | orchestrator |
| D43 | The four counts of a page are read from `requests` and `events` when the page is read, in the page's own transaction. No totals row is maintained. With no search and no exclusion the matching counts are the totals, read once. The scans behind an exclusion's counts and behind the distinct callers are accepted as they are. | Review 03.6 at 200,000 requests and 543,334 events: 5 to 9 ms for the request counts, 25 ms for the events, 18 to 45 ms for an exclusion, 23 ms for the callers. That is about five months of preprod, so a year stays near 100 ms, and a maintained total is one more thing the ingest transaction can get wrong. The service's tests hold each under 500 ms at 200,000 requests. | orchestrator |
| D44 | The backend never runs VACUUM. A network just backfilled relies on autovacuum before its caller search uses the trigram index. | Run in a scratch PostgreSQL 17 at 68ece48: 300,000 rows inserted in one statement into a table with a `gin_trgm_ops` index were autovacuumed 60 s later with no setting changed, and the fragment search then planned a `Bitmap Index Scan` on that index. | orchestrator |
| D45 | The ingest only inserts. It never deletes or rewrites an event, a transaction, a request or a caller, and the one removal is the wipe of a whole network (D12). A `requests` row is recomputed from the stored events of its request id inside the transaction that stores them, and a page that meets a row with no event fails: the service hides nothing. | Review 03.6: `request_callers` does not say which event named a caller and its foreign key has no ON DELETE, which matters only to a writer that removes an event. Review 03.3: a `requests` row with no event fails the whole page, so the ingest's rebuild test (step 04.2) is what keeps one from existing. | orchestrator |
| D46 | A network's cursor starts null and the first range starts at the start block. The cursor moves by `UPDATE ingest_state ... WHERE cursor_height IS NOT DISTINCT FROM <the value the cycle read>`, which is the first statement of the storing transaction: when it changes no row, the transaction rolls back before anything is inserted. The cursor block's hash is compared with the source once the cursor is not null. | Review 03.3: the schema leaves the three cursor columns null together until a block is processed, and `=` never matches a null. Taking the row lock first makes the loser of two cycles deterministic. | orchestrator |
| D47 | The api package exports `textWithoutUrlCredentials(text)`, which cuts every URL inside a text as `urlWithoutCredentials` cuts one. The wire applies it to a network's `error` and to every `failed` reason of an inspection, and the backend applies it to what it stores as `last_error` and to what it logs. | Review 03.3: `last_error` and `inspection.failed` reach the browser unfiltered, and the Blockfrost token sits in a URL (D13, D39). The wire is the one place every service passes, and the stored copy is cut as well so that the database holds no token either. | orchestrator |
| D48 | The sum of a lifecycle's three event lists is not moved to `packages/lib`. Step 04.5 deletes the UI's `signBidirectionalLifecycleEventCount` with the browser-side filters, since the status line then shows the service's counts. The in-memory service of the api package keeps the one copy in product code, and `eventsOf` of `contract.test.ts` stays as that test's own oracle. | Steps 03.4 and 03.6 counted three copies and expected the service to be a further user. The served service sums the count columns in SQL (D37), so after 04.5 one copy is left outside a test. | orchestrator |
| D49 | The backend's inspection is one function, `inspectTransactionForStorage(rawTransactionHex, notifications)`, called once per transaction with every sign bidirectional event it emitted, and it returns the `StoredInspection` of D38. A cell that does not decode as an evmType2 request record is stored as `{ failed: reason }` for that event. A transaction with no sign bidirectional event is stored with no raw bytes and no inspection. The ingest takes the function as a dependency typed by `StoredInspection` and lib's decoded event type. | Reconciles step 04.1's `inspectionForStorage(rawHex, requestId, notification)` with D34 and D38. The raw bytes are kept (D26), so a cell stored as failed loses nothing, and steps 04.1 and 04.2 run side by side against types that already exist. | orchestrator |
| D50 | Every request of the indexer adaptor ends after 30 seconds, as a failed read. The default poll interval (30 s, D29), tip margin (6 blocks, D28) and range (2,000 blocks, D21) are defined once, in the backend's configuration, and the ingest takes each as a required setting. | A request that never answers would hold a network's loop for ever with no error recorded. A default written in two modules drifts. | orchestrator |
| D51 | A stopped network is checked again every cycle and resumes when its stored identity matches its configuration again: after a wipe and a migration, or after the configuration is put back. Nothing else lifts a stop. | Report of 04.2. The loop of 04.10 already cycles a stopped network every interval. | orchestrator |
| D52 | An inspection result that holds a character PostgreSQL refuses (U+0000) is stored as `{ failed: reason }` for its transaction, and every text stored from outside loses that character first. | Review 04.8, blocking: an entry point name comes from the transaction's bytes, and a NUL in it failed the storing transaction on every retry, which stops the network for ever against D23. | orchestrator |
| D53 | The cursor moves only when the row still holds both the cursor and the identity the cycle read. Extends D06. | Review 04.8: a cycle that read before a wipe committed its events under the identity another process had recorded since, when the heights agreed. | orchestrator |

| D56 | The backend listens before it migrates. `/readyz` answers 200 from the moment every configured network's schema is migrated until a shutdown begins, and 503 outside that. | D57 | On SIGTERM or SIGINT the backend answers `/readyz` with 503, stops accepting requests, aborts every network's loop, waits at most 8 seconds for the cycles in flight, closes the pool and exits 0.
