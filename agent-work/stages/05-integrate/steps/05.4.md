## Goal

A verdict on every outcome of `../../../architecture.md`, from the merged code and from what you
ran, and every other defect of the whole branch marked `blocking` or `advisory`.

## Read first

- `../../../architecture.md`: `## Outcomes` first, then the design.
- `../../../decisions.md`
- The change itself: `git diff --stat 942e473...HEAD`, then the files that carry each outcome.

## Work

1. For each outcome, find the code that delivers it and run something that shows it: a test, a
   command, a request to the running thing. Reading alone never gives `met`.
2. Look for what a review of one stage cannot see: two stages that each pass and disagree where
   they meet, a decision the code does other than, a check that passes without the work.
3. You are given the code and the design. The builders' reports and the earlier reviews stay
   closed to you.
4. Step 04.14 had no review after it (D54, D55): read its merge alone, `m=$(git log --merges
   --grep 'Merge step 04.14' -1 --format=%H)`, then `git diff $m^1 $m`. Against a scratch
   PostgreSQL, run ingest cycles that meet what it fixed: an event name holding U+0000, a failure
   text of a million characters, an inspection the wire's schema rejects, one that cannot be
   serialised, one nested deeper than 64 levels. Each cycle must answer `stored`, and the page
   that then reads those rows through the service must answer. A cycle that fails on every
   retry, or a stored row the read path rejects, is `blocking`. Write `covered: step 04.14`
   under SUMMARY with what you ran.
5. The documentation: run every command `README.md`, `packages/backend/README.md` and
   `packages/ui/README.md` quote, and compare each section of `DECISIONS.md` with the rows of
   `../../../decisions.md` it rests on. A command that fails, or a reason the decisions do not
   give, is a finding. A command that needs the Blockfrost token takes it from the dev secrets
   inside the command. In `DECISIONS.md` check by a run or a read of the code, and not against the
   rows alone: the shape of a stored inspection, and every number the section on the indexer gives
   for calls a poll and the quota. Write `covered: the documentation` under SUMMARY.
6. The live run: `../../../probes/live-preprod.out.json` and the screenshot beside it are
   evidence for O1, O2 and O4 that you may cite, after you have read the probe that wrote them.
7. You change no file of the repository. What you start (a container, a server, a scratch
   folder) carries a name of your own and is removed before you report. Run one heavy thing at
   a time: the browser tests time out under load.
8. In `FINDINGS`, one line per outcome first: `O1: met <the evidence>` or
   `O1: not met <what is missing>`. Then one line per finding, starting `blocking:` (the code
   does other than the design says, loses data, leaks a secret, or an outcome is not met) or
   `advisory:` (anything else). Continue a line by indenting. `none` when there is no finding.

## Done when

`agent-work/stages/05-integrate/checks/05.4.sh` proves the report gives every outcome a verdict
and every finding a mark, and holds the lines `covered: step 04.14` and `covered: the
documentation`. It cannot prove a verdict is right: the orchestrator reads the evidence beside
each.
