## Goal

Every defect of the two contracts found before four builders work against them, each marked `blocking` or `advisory`.

## Read first

- `agent-work/architecture.md` and `agent-work/decisions.md`.
- `packages/api/src/` and `packages/backend/src/db/`, `packages/backend/src/source/`, whole.
- `packages/ui/src/components/midnight/` and `packages/ui/src/routes/midnight/explorer.tsx`: everything the UI renders from a lifecycle.

## Work

You are given the code and the design. The builders' reports stay closed to you. You change no file of the repository: what you write to test a claim lives in your scratch folder and is removed. Attack each heading, and write a line `covered: <heading>` in your report for each, with what you did.

1. `the UI's needs`: list every value the explorer page and an expanded row render or compute from Midnight data today. For each, name the wire field that carries it. A value with no field is `blocking`.
2. `no gaps`: can the tables and the port express the design's ingest (one transaction that stores a range and moves the cursor on condition)? Can an event be stored twice, or a request row disagree with its events after a retry? Does a transaction that notifies two requests keep a record for each (D34)?
3. `one row per row`: does one row of the view hold everything one list row and its expansion need from the backend (O6)?
4. `network separation`: can any statement of one network touch another's schema? Does the wipe drop only its own?
5. `secrets`: can the token reach a log, an error body or a response through any type here (D13)?
6. `the indexes`: run the list, the search, the exclusion and the count against a database you seed with 200,000 requests. Start a PostgreSQL 17 container of your own named `explorer-03-3-pg`, bound to `127.0.0.1`, and remove it. Report the timings and any plan with a sequential scan of `events`.
7. `the fakes`: does the in-memory service answer as the routes over the real view will (ordering, paging cursor, search rules, exclusion)? A difference a UI test could pass on is `blocking`.

In `FINDINGS`, one line per finding, starting `blocking:` (the code does other than the design says, loses data, leaks a secret, or a check passes without the work) or `advisory:` (anything else). Continue a line by indenting. Write `none` when there is none. File your report first, then run the check.

## Done when

`checks/03.3.sh` proves the report covers the seven headings and marks every finding. It cannot prove a finding is right: the orchestrator reads the evidence beside each.
