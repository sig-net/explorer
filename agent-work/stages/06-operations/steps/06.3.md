## Goal

`yarn drills` starts REAL backend processes against a local stand-in for the indexer and a real
Postgres, breaks things on purpose, and passes only when each failure ends as section 5
promises. The unit tests of stage 04 prove the rules inside one process with a fake: the drills
prove them across process death, with the real chain source, the real HTTP host and the real
commands.

## Read first

- `../../../architecture.md`, sections 5 and 9. The stage's `stage.md`: gate G24.
- `packages/backend/src/chain-source/indexer/` (the queries the real chain source sends, which
  the stand-in must answer) and `src/chain-source/fake-chain-source.ts` (the scripting the
  stand-in reuses).
- `packages/backend/src/main.ts`, `src/commands/`, `packages/api/src/http.ts`.

## Work

1. `drills/indexer-double.ts`: a small HTTP server, Node's own `node:http`, that answers the
   GraphQL queries the indexer chain source sends, from a chain it holds in memory, built on
   the fake chain source's scripting. It has a control route to script it while it runs:
   advance the head, add events, replace a block, hold an event back, fail a range, answer a
   range differently. It is a drill tool: it lives under `drills/`, nothing in `src/` imports
   it.
2. `drills/harness.ts`: start and stop a backend process (`node src/main.ts start` with an
   environment pointing an `undeployed` network at the double, on a scratch database and free
   ports), `kill -9` it, wait for a condition through the HTTP API, run a command, and read
   the tables. Every process and database it makes is torn down, also when a drill fails.
3. `drills/*.drill.test.ts`, one file per drill, run by vitest with long timeouts and no
   parallelism:
   - Death mid catch-up: `kill -9` while ranges are being written, start again, and at the end
     the events equal the double's chain exactly and the audit finds no difference. Repeat ten
     times at random moments.
   - Two writers: a second `ingest` process for the same database does not write while the
     first lives, and takes over when the first is killed.
   - The chain changes under the checkpoint: the double replaces a processed block. The
     network becomes `halted` with a reason, `listNetworks` shows it over HTTP, a restart
     leaves it halted, and no event row changed.
   - The indexer changes its mind: the double serves a processed range with one event more.
     The trailing re-read halts the network.
   - A range that never succeeds: the double fails one range for ever. The checkpoint stops
     just before it, the network halts after the configured attempts, and nothing beyond the
     range is stored.
   - Reset and recover: after a halt, `reset-network` with its flag, the double repaired,
     `start`: the network indexes from the start block to the head, equal to the chain.
   - Split roles: one `ingest` process and one `serve` process on one database serve the same
     pages as one process with both roles.
   - The schema is wrong: a column is added by hand. `start` refuses, names the command, and
     the row count is unchanged.
4. Scripts: `drills` in the backend package and at the root. The drills are NOT part of
   `yarn check`: they take minutes and start processes.
5. `yarn lint`, `yarn build`, `yarn check`, `yarn drills`. Commit. Put a line starting `G24:`
   with `holds` or `fails` in `FINDINGS`, and for a drill that failed because the product is
   wrong, the file and line of the fault: you do not fix `src/`, which is not in your scope.

## Done when

tools, all checks pass, `yarn drills` passes when run again here, and no process, port or
scratch database is left. It cannot prove a drill kills at the moment that matters: 06.4 reads
the first drill's timing.
