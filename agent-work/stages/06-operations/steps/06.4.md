## Goal

The audit, the commands and the drills have been attacked by someone who did not write them,
and every finding is marked `blocking` or `advisory`. You change no file. You read the code and
run it, not the builders' reports: do not open anything under `agent-work/reports/`.

## Read first

- `../../../architecture.md`, sections 5 and 9, and `../../../decisions.md`, whole.
- `packages/backend/src/audit/`, `src/commands/`, `src/db/`, `packages/backend/drills/`.

## Work

Start the local Postgres, make a scratch database of your own, migrate it, and fill it by
running the backend against the drills' indexer double for a few hundred blocks. Drop the
database and stop every process before you report. Then, in this order:

1. The audit against your own plants, not the builders': by SQL, on your scratch database,
   one at a time and restoring between each: swap the payloads of two events of one block,
   change one event's `block_position`, move an event to another request id while keeping the
   row consistent with itself, change `processed_block_hash`, change one count in a sign
   request row, delete the oldest event. Each plant the audit does not report is `blocking`.
2. The audit beside a live ingester: does it report differences that are only the ingester's
   progress? Does `--report-only` write anything at all (compare a dump before and after)?
3. Erasing by accident: every way to run `wipe` and `reset-network`. A flag spelled wrongly,
   the flag of one given to the other, a network name that does not exist, a network name in
   capitals, the flag in an environment variable. Does `start`, `migrate`, `audit` or
   `schema-state` ever delete, drop, truncate or alter? Search the SQL the process sends
   (`log_statement = all` on your scratch database) for those words during a `start`.
4. The reset: does it leave a row of the network anywhere (search every table for the network
   id afterwards)? Does it touch another network or the Ethereum outputs? Can it run while an
   ingester for that network lives?
5. The schema check: is `mismatch` detected for a dropped index, a changed column type, an
   extra table? Which of those does the design need caught, and which does the hash of the
   applied migration catch? State plainly what the check proves and what it does not.
6. The drills: for the first drill, is the process ever killed INSIDE a transaction, or always
   between two? Read the timing and say. For each of the others: would it pass if the product
   did nothing (a halt that was never set, a lock never taken)? Break the product in a copy of
   one file for two drills of your choice, run them, see them fail, restore from the copy.
7. Leftovers: after `yarn drills`, a process, a listening port or a scratch database.

File your report FIRST, then run the exit check. In `FINDINGS`, each finding is one line
starting `FINDING <n> (blocking): ` or `FINDING <n> (advisory): `, with the file and line and
what you ran. `blocking` means: the code does other than the design says, loses data, leaks a
secret, or a check passes without the work. Everything else is `advisory`. With no finding at
all, write the line `NO FINDINGS`. Add one line `ATTACKED: ` listing which of the seven items
you completed.

## Done when

`checks/06.4.sh` proves the report marks every finding and names what was attacked, and that no
change, process or scratch database was left behind. It cannot judge the findings: the
orchestrator applies gate G25 to them.
