## Goal

The whole change, from the baseline to the head of the parent branch, has been read against the
design by someone who built none of it, and every finding is marked `blocking` or `advisory`.
You change no file. You read the code and run it, not the builders' reports: do not open
anything under `agent-work/reports/`.

## Read first

- `../../../architecture.md` and `../../../decisions.md`, whole. The `orchestrator` rows of the
  decisions are where the design changed during the work: the code must match THEM.
- `git diff --stat <baseline>..HEAD`, the baseline being the `baseline` of
  `../../../task.json`, then the change itself, package by package.

## Work

Run first, on the parent branch: `yarn install --immutable`, `yarn lint`, `yarn build`,
`yarn check`. Then, in this order:

1. The design, section by section, 1 to 10: for each sentence that states something the system
   does or never does, find where the code does it. A sentence with no code, and code that
   contradicts a sentence, are findings. Do section 5 last and slowest.
2. `docs/architecture.md` against the code: it claims to describe the system as built. Each
   claim that is not true of the code is `blocking`: a wrong document outlives this task.
3. The README's local run, top to bottom, on a fresh clone of the parent branch in a temporary
   folder, typing only what it says. Where it fails or assumes something unsaid: a finding.
4. What must be gone: the probes, the UI's event store and its settings, every fake outside
   tests, every `TODO`, `FIXME`, skipped test without a reason, commented-out code, and file
   that nothing imports (`git grep` each new file's exports for a consumer).
5. Names after the change: a name that promised one thing at the baseline and holds another
   now (a context, a config type, a folder), and a qualified name beside its unqualified twin.
6. The boundaries: `lib` and `api` in both runtimes, the dependency direction, no URL in any
   reply type, no verdict, the two WebAssembly files with the ledger one lazy, no cursor
   class, no hand-rolled UI primitive, no root-absolute URL to the app's own files.
7. The comments of the new code: a comment that tells history, restates the code, or documents
   its callee. Sample thirty across the packages. A pattern is one `advisory` finding with
   three examples, not thirty findings.
8. The workflows and the images against their own header comments and against D20, D26, D29.
9. The user's advisory list: collect every `advisory` finding of the earlier reviews that
   `decisions.md` records as left for the user, and say for each whether it still stands.

File your report FIRST, then run the exit check. In `FINDINGS`, each finding is one line
starting `FINDING <n> (blocking): ` or `FINDING <n> (advisory): `, with the file and line and
what you ran. `blocking` means: the code does other than the design says, loses data, leaks a
secret, or a check passes without the work. Everything else is `advisory`. With no finding at
all, write the line `NO FINDINGS`. Add one line `ATTACKED: ` listing which of the nine items
you completed. If your report does not fit its budget, keep every `blocking` finding whole and
shorten the advisory ones to a line each.

## Done when

`checks/07.5.sh` proves the report marks every finding and names what was attacked, and that the
review left no change behind. It cannot judge the findings: the orchestrator applies gate G27 to
them, and then tells the user the task is ready and what is left for them to decide.
