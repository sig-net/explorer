## Goal

The two workflows build what the repository now holds: `pages-deploy` builds the UI from the
workspace with the backend's URL and publishes `packages/ui/dist`, and `docker-publish` publishes
both images (D26) for both architectures. This is the last commit of the task, and whether it is
pushed is gate G26.

## Read first

- The stage's `stage.md`, beside `steps/`: gate G26. `../../../decisions.md`: the verdict of
  G12, and D16, D20, D26, D29.
- `.github/workflows/pages-deploy.yml` and `.github/workflows/docker-publish.yml`, whole,
  comments included: every rule a comment states there still holds after your change.
- `Dockerfile`, `packages/backend/Dockerfile`, the root `package.json` scripts.

## Work

1. `pages-deploy.yml`, job `build`: the commands stay `yarn install --immutable`, `yarn lint`,
   `yarn build`. The build gets `VITE_EXPLORER_BACKEND_URL` from the repository variable
   `vars.EXPLORER_BACKEND_URL` (a variable, not a secret: the URL is public once the site is
   built). Where the backend is hosted is not decided (D16): an unset variable builds a site
   that says no backend is configured, and a comment in the workflow says so. The copy of
   `index.html` to `404.html` and the uploaded path become `packages/ui/dist`.
2. `docker-publish.yml`: publish two images from the same tag, `ghcr.io/<repository>` from the
   root `Dockerfile` and `ghcr.io/<repository>-backend` from `packages/backend/Dockerfile`,
   each for `linux/amd64` and `linux/arm64`, each with the manifest tags the workflow gives
   today. Keep the structure that makes it safe: the arm64 build has no credentials and hands
   its tarballs over as artifacts, `publish` alone pushes, the tag is verified first, nothing
   is cached. Use a matrix over the two images or two explicit sets of steps, whichever keeps
   those rules readable.
3. Keep every action pinned to the commit hash it has today. Add no new action. Add no
   trigger, and no `pull_request` workflow (D29). Keep `permissions` as narrow as they are.
4. Update the header comment of each file so that it describes what the file does after your
   change, in the present tense.
5. Check what can be checked here. Both files parse as YAML:
   `python3 -c "import yaml,sys; yaml.safe_load(open(sys.argv[1]))" <file>` (PyYAML is on this
   machine). Then run by hand, in your worktree, the exact commands of the `build` job in
   order, with `EXPLORER_BASE_PATH=/explorer/` and a backend URL, and both `docker build`
   commands of the publish job. A workflow cannot be run from here: say so in your report,
   and say that the first tag after the merge is its first real run.
6. Commit. Then read the verdict of G12 in `decisions.md`. `holds`: push your branch as your
   rules allow. `fails`: do NOT push, and say in your report, under a line starting
   `NOT PUSHED:`, the repository, the branch, the folder and the permission that is missing
   ("Workflows").
