## Goal

`Ingester` runs the loop of section 5 for one network: whole ranges, ascending, the checkpoint
advanced in the same transaction as the rows, one writer, a halt in place of a skip. Every rule
of that section has a test that drives the loop with the fake chain source against a real
Postgres.

## Work

1. `ingester/ingester.ts`: a class built from a network id, its deployment (the deployments
   repository's resource type), a chain source, the repositories, the network lock, the unit of
   work, a logger, a clock (`now: () => Date`) and settings: `safetyMargin`, `rangeSize`,
   `rereadBlocks`, `pollIntervalMs`, `maxRangeAttempts`. Their defaults are constants defined
   here, each with the gate its number came from. `maxRangeAttempts` defaults to 5.
2. Three methods. `start()` does what a network needs once and answers whether it holds the
   lock. `runOnce()` is one turn of the loop and returns what it did: it throws if `start()`
   has not succeeded. `run(signal)` calls `start()` every poll interval until it holds the
   lock (so a second process waits, and takes over when the first dies), then repeats
   `runOnce()` until the signal aborts, then releases. Tests drive `start` and `runOnce`. No
   timer in a test.
3. `start()`: `tryAcquire` the network's lock. Then compare the configured deployment with the
   stored one. Equal: go on. None stored: `contractExistsAt(start_block - 1)` must be false
   for both contracts, then store the deployment and a checkpoint at `start_block - 1` with
   that block's hash. A start block of 0 has no block before it: skip the existence check,
   store the checkpoint at -1 with an empty hash, and skip the hash check while it is at -1.
   Different: refuse, with a message that names the reset command and no value.
4. One turn, exactly as section 5: head, target, the hash check under the checkpoint, ranges.
   For each range, read the events and the range's last block from the chain source FIRST,
   turn each event into its stored form with `toSignetEvent`, then ONE transaction: insert the
   events, `applyEventsToSignRequests`, advance the checkpoint. Then the trailing re-read: read
   the last `rereadBlocks` again and compare with the stored events, event for event.
5. Halting: a changed hash, a `ChainDataConflict`, a re-read that differs, or a range that has
   failed `maxRangeAttempts` turns in a row (counted in memory: a restart counts again) halts
   the network with a reason, in its own transaction, and ends the loop. A halted network
   stays halted across restarts: `start()` on it succeeds and `runOnce()` does nothing but
   report it. A failure below the limit leaves the checkpoint where it was.
6. `head_block` and `update_time` are written every turn, also with nothing to read.
7. Tests on scratch databases with the fake chain source, one per rule, the rule in the test's
   title: begins at the start block. A contract that exists before the start block refuses.
   Ranges are whole and ascending and the checkpoint never passes head minus the margin. A
   crash before commit replays to the same rows: wrap the real unit of work, in the test, in
   one that runs the work and then throws, once. A replay that meets a different row halts:
   seed a differing event above the checkpoint through the repository, then run. A changed
   hash halts. A late event is caught by the re-read and halts. A range that keeps failing
   halts and is never stepped over. A second ingester's `start()` does not get the lock. A
   changed deployment refuses. A halted network stays halted after a new `start()`. After
   every scenario the sign request rows equal `deriveSignRequest` over the stored events.
8. `yarn lint`, `yarn build`, `yarn check`. Commit.

a test is titled for each rule and none is skipped or left to do, and all checks pass. It cannot
prove the tests assert what their titles say: 04.11 reads them one by one.
