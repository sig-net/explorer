## Goal

Every way the ingest or the source could lose an event, store one twice, move the cursor past missing data or leak the token, found and marked `blocking` or `advisory`.

## Read first

- `agent-work/architecture.md` ("Ingest", "Store", O4, O5) and `agent-work/decisions.md` (D06, D12, D13, D23, D27, D28, D36, D38, D45 to D47, D49, D50).
- `packages/backend/src/ingest/`, `packages/backend/src/source/`, `packages/backend/src/inspection/`, `packages/backend/src/db/`, whole.

## Work

You are given the code and the design. The builders' reports stay closed to you. Attack each heading, and write a line `covered: <heading>` in your report for each, with what you ran.

1. `atomicity`: find any path on which the cursor is written outside the transaction that stores its range, or the transaction commits with part of a range.
2. `interleavings`: two processes on one network, a crash between any two statements, a retry after a commit whose answer was lost, a loop that meets a database that is down or a schema that is being wiped. Write a test for each you can and run it against a PostgreSQL you start as `agent-work/lib/checks.sh` does (remove it after).
3. `the source`: paging by offset while new events arrive, a contract with more than one page in a range, an empty range, a range above the tip, an event whose block is outside the range, both roles at one address, a request that never answers.
4. `the inspection`: a transaction that notifies two requests, one notification that fails beside one that reads, bytes that do not deserialise. Is what is stored the `StoredInspection` of D38, and does the `lifecycle` view serve each event its own entry?
5. `the request rows`: can a `requests` row or the `request_callers` of a request disagree with its events after any order of arrival or any retry? Can a `requests` row exist with no event (D45)?
6. `stopping`: does every identity mismatch stop before any write, and does a wipe followed by a cycle index again from the start block?
7. `secrets`: grep and read every log line, thrown message, stored `last_error` and stored `failed` reason for a URL that could carry its query string or a user and password (D47).
8. `the checks`: does a test named in `agent-work/stages/04-build/checks/04.1.sh`, `agent-work/stages/04-build/checks/04.2.sh` or `agent-work/stages/04-build/checks/04.10.sh` pass without testing what its title says?

In `FINDINGS`, one line per finding, starting `blocking:` (the code does other than the design says, loses data, leaks a secret, or a check passes without the work) or `advisory:` (anything else). Continue a line by indenting. Write `none` when there is none. The `covered:` lines go under SUMMARY. A report holds at most 6000 bytes: keep the evidence to the command and its decisive line. File your report first, then run the check.

## Done when

`agent-work/stages/04-build/checks/04.8.sh` proves the report covers the eight headings and marks every finding. It cannot prove a finding is right: the orchestrator reads the evidence beside each.
