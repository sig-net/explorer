## Goal

`NetworkServiceImpl` and `SignRequestServiceImpl` implement their `@explorer/api` interfaces over
the repositories. The same test suite passes against each implementation and against the fake
of `@explorer/api/fakes`, so the UI built on the fake meets the same behaviour.

## Read first

- `../../../architecture.md`, sections 3 and 7.
- `packages/api/src/network/network-service.ts`, `packages/api/src/sign-request/sign-request-service.ts`
  and the two fakes in `packages/api/src/fakes/`.
- `packages/backend/src/repositories/` (interfaces). `packages/backend/src/config/` may not be
  merged when you start: take what you need of the configuration as a constructor argument of
  a type you define from the `MidnightNetworkStatus` resource, never by importing `config/`.

## Work

1. `services/sign-request/sign-request-service-impl.ts`: the three methods over the sign
   requests and events repositories. `listSignRequests` passes the filters and the token
   through and returns the next token. `getSignRequest` returns the row with its events in
   chain order, and reports an unknown request as the interface says. A network that is not
   configured is refused with a message, for every method.
2. `services/network/network-service-impl.ts`: built from the per-network facts (configured or
   not, the deployment, the indexer's HOST) and the checkpoint repository. `listNetworks`
   returns all four networks, each with its status. `processedBlockTime` comes from the stored
   events only if the resource says so: otherwise from what the checkpoint holds. Never a URL.
3. `services/sign-request/sign-request-service.contract.ts`: a function that takes a way to
   build the service over a given history of events, and declares the behavioural tests: every
   filter, paging that sees each row once, an unknown request, a row that changes after more
   events. Run it twice: over the fake (`@explorer/api/fakes`) and over the implementation on
   a scratch database filled through the repositories and `applyEventsToSignRequests`. The
   same for the network service.
4. If the two disagree on any case, the contract of stage 03 decides: fix the implementation
   when it is wrong. When the FAKE is wrong, report it under `STEP CORRECTIONS` with the
   failing case and leave the case skipped with that reason: the fake is not in your scope.
5. `yarn lint`, `yarn build`, `yarn check`. Commit.

## Done when

`checks/04.5.sh` proves both implementations exist, each has a contract suite that is run over
the fake and over the implementation, no skipped case is left without a reason, nothing in the
two folders can return a URL, and all checks pass.
