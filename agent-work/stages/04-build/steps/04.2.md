## Goal

Every repository interface of stage 03 has a Drizzle implementation, the unit of work runs
several of them in one transaction, and `applyEventsToSignRequests` keeps the aggregate table
equal, after every batch, to what `deriveSignRequest` gives over all stored events. A property
test proves that equality.

- `../../../architecture.md`, sections 4 and 5 (the idempotence rule above all).
- `packages/backend/src/repositories/` (the interfaces), `src/db/schema.ts`,

## Work

1. `repositories/sql/unit-of-work.ts`: the demo's shape, an `AsyncLocalStorage` holding the open
   transaction, `runInTransaction` joining an open one, and `currentExecutor(database)` that
   every repository below runs on.
2. One `<table>-repository-sql.ts` per interface. Every row read is parsed with its resource's
   zod schema, so a row the schema refuses is an error and never a silent cast.
3. The events repository's insert is the idempotence rule of section 5, and it is the heart of
   this step: inserting a row whose key exists and whose content is IDENTICAL is a no-op.
   Inserting a row whose key exists and whose content DIFFERS throws the `ChainDataConflict`
   of the interface file, naming the key. Identical and different are decided by `sameChainEvent` of the interface file and by
   nothing else. It never updates and never skips silently.
4. The sign requests repository: `listSignRequests` by keyset on the sort key, newest first,
   with the search fragment (request id or caller, using the trigram indexes), excluded callers
   and states. The page token encodes the last row's sort key and is checked when decoded: a
   token that does not decode is a refusal the service can report, not an exception.
   `listCallers` returns distinct callers.
5. `repositories/sql/network-lock-sql.ts`: the lock interface over `pg_try_advisory_lock`, on
   ONE client taken from the pool and kept until `release()`, never on a pooled query. A test
   shows a second `tryAcquire` gets nothing until the first releases, and gets it when the
   first holder's connection is ended.
   `sign-requests/apply-events.ts`: `applyEventsToSignRequests(events: SignetEvent[])` runs
   inside the open transaction. For each request id among the batch's decoded events it reads that request's
   stored events and writes the row `deriveSignRequest` gives. Start with this simple, exact
   form. Make it incremental only if a test shows the simple form is too slow at 100 events a
   request.
6. Tests on scratch databases:
   - each repository's reads and writes, and each list filter alone and combined
   - a walk through every page sees every row once, with rows sharing a first block
   - the three insert outcomes of item 3
   - the property: for 200 random event histories (random request ids from a small pool,
     random kinds, random order of blocks, split into random batches), after each batch the
     table equals `deriveSignRequest` applied to every stored event of each request
   - a transaction that throws after inserting events leaves no event and no row behind.
7. `yarn lint`, `yarn build`, `yarn check`. Commit.
