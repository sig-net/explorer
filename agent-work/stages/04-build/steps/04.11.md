## Goal

The code that decides whether an event is lost has been attacked by someone who did not write
it, and every finding is marked `blocking` or `advisory`. You change no file. You read the code
and run it, not the builders' reports: do not open anything under `agent-work/reports/`.

## Read first

- `../../../architecture.md`, sections 4, 5 and 6, and `../../../decisions.md`, whole.
- `packages/backend/src/chain-source/`, `src/repositories/sql/`, `src/sign-requests/`,
  `src/ingester/`, `src/db/`, with their tests.

## Work

Start the local Postgres (`docker compose -p explorer up -d --wait postgres`) and run the
backend's tests once, so you know they pass before you doubt them. Then attack, in this order.
You may write scratch tests to try an attack. Do not commit them and leave no file behind.

1. Each rule of section 5, one by one: find its test in `src/ingester/`, read what it ASSERTS,
   and decide whether the test would fail if the rule were broken. For three rules of your
   choice, break the rule in the code, run the test, see it fail, and restore the file from a
   copy you made first. A test that still passes is a `blocking` finding.
2. The transaction boundary: is there any path where events are committed and the checkpoint
   is not, or the reverse? Any `await` inside the range's work that is not awaited, which would
   run outside the unit of work?
3. The idempotence rule: what does a replay do when a row is identical but for something that
   may legitimately differ between two reads of the same chain (the indexer's event id, the
   payload's padding, a timestamp's precision)? Is that a no-op, a halt, or silent corruption,
   and is it what the design wants?
4. `eventsInRange`: construct by hand an indexer answer that is wrong and passes every check
   (a missing last page, an event of another contract, two pages swapped, a range answered for
   a different range). Each one that passes is a finding.
5. `blockPosition`: with one contract in both roles, with two contracts emitting in one block,
   and with a block read in two different ranges, is the position of an event always the same?
6. The single writer: can two processes both believe they hold the lock (a lock taken on a
   pooled connection that is returned to the pool, a lock lost when the connection drops)?
7. The halt: once halted, can anything but a reset make the network index again? Does a halt
   lose the reason on restart?
8. The aggregate: think of a history where the table and a rebuild from events differ (events
   of one request split across two ranges, a request whose first event arrives in a later
   range than its response, an undecodable event with a request id's bytes in it).
9. The start: `start_block - 1` when the start block is 0, and a checkpoint hash for a block
   the indexer cannot give.

File your report FIRST, then run the exit check. In `FINDINGS`, each finding is one line
starting `FINDING <n> (blocking): ` or `FINDING <n> (advisory): `, with the file and line and
what you ran. `blocking` means: the code does other than the design says, loses data, leaks a
secret, or a check passes without the work. Everything else is `advisory`. With no finding at
all, write the line `NO FINDINGS`. Add one line `ATTACKED: ` listing which of the nine items
you completed, and for item 1 the three rules you broke.
